這輪以 `main` 的 `f4acc1c92366b4210f2aaecdcd1cd2a2ad9368e1` 為準。你這次落實了 class 分組、直接讀取選定 alternate、直接執行已選規則，以及探索清單重用，也加入了連結正式原始碼的測試。就這幾項修改的呼叫路徑，我沒有確認到新的替換結果回歸；繼續往下檢查，找到一項既有定位錯誤、一個這次改動帶來的記憶體取捨，以及幾處值得接著整理的地方。 
我在 Linux 執行了局部 C++ 驗證，普通版本與 AddressSanitizer／UndefinedBehaviorSanitizer 版本結果一致。這些是原始迴圈摘錄與合成模型，沒有執行完整 macOS App，也沒有把儲存庫中的完整測試套件跑過。下面的操作次數與記憶體數字，都只代表相應局部測試。
最先需要修正的是 `Sources/FontLayout/GAPositioning.cpp:187–201` 的 mark-to-mark 父標記搜尋。目前 `mark()` 遇到前一個 mark 不在目標 coverage 裡，會繼續往前找，直到找到某個被收錄的 mark；同時，這個函式沒有接收 `Lookup`，搜尋父標記時也沒有套用 mark filtering set 或 mark attachment type。OpenType 的規則是：先按 LookupFlags 略過應忽略的字形，取得前一個候選，再判斷該候選是否在 mark2 coverage 裡。不能因為 coverage 不匹配，就繼續往前尋找另一個。 [learn.microsoft.com](https://learn.microsoft.com/en-us/typography/opentype/spec/gpos)
具體反例是輸入「基底＋標記 A＋標記 B＋標記 C」，目前正在定位 C，mark2 coverage 只收錄 A，lookup flags 為零。此時前一個標記是 B，這個 lookup 應不套用；現有程式卻會跨過 B，把 C 附著到 A。另一個反例是 coverage 同時收錄 A、B，但 mark filtering set 排除 B：程式仍會選 B，應該選 A。我已在摘錄的搜尋迴圈中重現這兩種結果。這項會影響自家引擎計算的候選字形位置，不能據此推定由系統 TextView 排版的 Characters 視圖也有相同錯誤。 
修法可以很集中：讓 `mark()` 接收 `Lookup`，將 type 6 的父標記選擇獨立處理，按 flags 略過字形後，只檢查第一個未被略過的候選；不匹配 coverage 就返回未套用。不要把這個停止規則直接共用到 type 4／5，因為 mark-to-base、mark-to-ligature 的尋找目標不同。這次很適合直接在新增的正式 C++ 測試中補上兩個合成 GPOS 案例。
這次優化還有一個值得調整的記憶體取捨，位於 `GASubstitutionEngine.mm` 的 `Resource` 建構函式。現在 `featurePlans` 會在載入字型時，把每個 feature 的所有 value 完整展開，並跟著共享 resource 常駐。這確實避免了原先反覆建立陣列，但展開數量取決於各 feature 的 `maximum` 總和；多個 feature 共用同一個大型 alternate lookup 時，仍會各自展開一份 value 範圍。
我用「256 個 feature，每個有 32,768 個 value」的合成描述測試，得到 8,388,609 個項目，包含 default plan。元素本身約佔 64 MiB；在這次環境的 vector 成長策略下，capacity 佔到 128 MiB。原始的 256 組「feature／maximum」只需 2 KiB。這不是實際字型載入測量，也不表示一般字型會有這種規模，但能看出常駐展開的成本。上一版也會在查詢時產生大陣列；這次改動讓這項成本提前到載入階段，並延長到 resource 的整個生命週期。 
我更建議保留緊湊的 feature／maximum 清單，再用一個小型 `forEachPlan` 或訪問函式依序產生 `(feature, value)`。如此既不用每次配置完整陣列，也不用常駐展開結果，順序與來源標籤都可以保持。局部測試比較了 200 組合成描述，列舉內容與順序一致。這裡不需要引入 coroutine 或新框架，也不必靠截斷清單來省記憶體；它只是資料表示的精簡，真正需要執行的探索次數並不會因此減少。
下一個比較直接的效能改善，是 `Sources/FontLayout/GASubstitution.cpp:130–140` 的 `Substitution::ligate()`。它逐一遍歷首尾 component 之間的位置，對每個位置呼叫 `std::find(positions.begin(), positions.end(), pos)`，判斷是否為參與連字的 component。`positions` 已經按位置遞增，因此這裡不需要每次從頭搜尋。當 K 個 component 連續排列時，單是這個 membership 檢查就會做約 K²／2 次比較。
改成單向游標即可：遍歷 `pos` 的同時，與下一個 component 位置比較；相等就推進游標，不相等才處理被略過的 mark。既有的 component 歸屬、source 合併與從右往左刪除仍然保留。我比較了 1,000 組包含間隔位置的合成案例，取得的略過位置完全一致；8,192 個連續 component 的比較次數由 33,558,528 次降至 8,192 次。這個改動比進一步改寫整套替換 buffer 更小，也比較容易用你現在的 executor 測試確認。
定位流程則有一處「慢查詢取消不了」的缺口，值得先於更複雜的快取優化處理。`positionsForGlyphIDs:content:` 沒有 cancellation 參數，`Positioning` 建構自己的 `Budget` 時也沒有傳入取消訊號；外層即使已經因新輸入而取消查詢，正在執行的一次定位仍需自己完成。尤其 `GAPositioning.cpp` 的 `pen()` 在 RTL 模式下，每次都從指定位置重新累加到序列末尾，attachment 多時會形成平方級工作量，而這段迴圈與 attachment resolution 本身沒有輪詢取消。 
在 4,096 個字形、2,048 個基底／標記 attachment 的數值模型中，這條 RTL 路徑做了 8,386,560 次 suffix 元素訪問。這不代表一般短候選會慢，但較長的多 GID 候選會放大成本。我的建議是先把 cancellation 從查詢傳入定位，再讓長迴圈定期檢查；遇到取消，應中止整個過期查詢，不能把取消轉成零原點或空 positions，當成正常 fallback 繼續發布。
至於將 RTL pen 改成一次計算 suffix cache，暫時不宜直接當作行為不變的優化。原始註解已經表明，它刻意保留向前累加的順序；反向累加確實可能改變浮點結果，局部測試也能顯示差異。需要先決定位置比較允許多大的誤差，再修改這部分。相較之下，補上取消不需要改變正常完成查詢的定位結果，收益也比較明確。
新增測試本身也還有一個可以補強的地方：目前一部分是會判定成敗的回歸測試，另一部分仍只是產生對照紀錄。`FontLayoutRegression.cpp` 已經對 alternate、class 0、候選順序和立即取消做了實質 assertions；但後面大量 `run()` 案例遇到 `InvalidTable` 或取消後，只將狀態印出。`run-font-layout-regression.sh` 把輸出存成檔案便宣告通過，沒有自動核對那些案例的期望結果或先前紀錄。這不影響你這次手動做前後比較的價值，但後續改動不能單靠腳本成功退出，就認定整批案例都沒有回歸。 
原生 engine 測試也有類似情況：目前主要檢查首次與快取查詢結果是否一致。假如某條路徑錯誤地每次都回傳 `nil`，兩次都轉成 `NSNull`，一致性檢查仍然成立；取消案例則主要記錄結果，沒有逐一斷言應有狀態。建議先補上「未提供取消訊號時不得無故回傳 nil」、幾組已知非空輸入的基本輸出契約，以及這次 mark-to-mark 的確定預期。再提供可選的 transcript 比較模式，讓不一致導致非零退出。使用系統字型的紀錄比較應在相同環境進行；跨環境長期保存的期望值，更適合使用可控的合成 fixture。 
取消測試還可以順便調整目標：正常結果、取消後不發布過期結果，以及合理的取消回應，才是需要維持的行為；輪詢次數不一定要在每次優化前後完全相同。否則增加必要的取消檢查，也會被單純的 transcript 差異視為回歸。
就下一輪的順序，我會先修 mark-to-mark 並加入正式測試，再把展開的 `featurePlans` 改成緊湊列舉、把連字 membership 改成游標，然後補齊定位的取消傳遞。已經改好的 class 索引和 alternate 解碼，暫時沒有必要繼續拆分或增加抽象。另核對到 GPOS 後才套 legacy kern 的順序仍然保留，上輪那項正確性修正尚未包含在這次優化中。
